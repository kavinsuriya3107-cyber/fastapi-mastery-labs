The project demonstrates the core mechanics of client-server architecture, endpoint structures, and interactive API documentation using Python and the FastAPI framework.

## 🚀 Getting Started

Follow these steps to set up and run the API server locally on your machine.

### 1. Prerequisites
Ensure you have Python installed on your system. You can verify by running:
```bash
python --version
```

### 2. Environment Setup
Create an isolated Python virtual environment (`venv`) to keep the project dependencies separate from your global system environment.

```bash
# Create the virtual environment
python -m venv venv
```

### 3. Activation
Activate the virtual environment depending on your operating system and terminal shell:

* **Windows (PowerShell)**:
  ```powershell
  Set-ExecutionPolicy -ExecutionPolicy RemoteSigned -Scope Process
  .\venv\Scripts\Activate.ps1
  ```
* **Windows (Command Prompt / cmd)**:
  ```cmd
  venv\Scripts\activate.bat
  ```
* **macOS / Linux (Bash/Zsh)**:
  ```bash
  source venv/bin/activate
  ```

Once activated, your terminal prompt will display `(venv)`.

### 4. Install Dependencies
Install the required packages using pip:
```bash
pip install -r requirements.txt
```

### 5. Running the API Server
Start the local development server with live reloading enabled:
```bash
uvicorn main:app --reload
```
* The `--reload` flag instructs Uvicorn to watch your python files for changes and automatically restart the server whenever you edit the code.

## 📡 API Endpoints

Once the server is running, it will listen on `http://127.0.0.1:8000`. The following endpoints are available:

| Method | Endpoint | Description | Sample Response |
| :--- | :--- | :--- | :--- |
| **GET** | `/` | Welcomes user, displays framework, and shows learning phase. | `{"message": "Welcome to your API Mastery Lab!", "status": "online", ...}` |
| **GET** | `/api/v1/health` | Performs health-check on core services (server & database status). | `{"status": "healthy", "database": "disconnected"}` |
| **GET** | `/docs` | Interactive OpenAPI/Swagger UI. | *HTML Webpage* |
| **GET** | `/redoc` | Alternative API documentation generated by ReDoc. | *HTML Webpage* |

## 🎨 Interactive API Documentation (OpenAPI)

FastAPI automatically reads the codebase and generates interactive API documentation. 
* **Swagger UI**: Visit `http://127.0.0.1:8000/docs` in your browser. You can inspect endpoints and execute requests directly from the browser window using the **"Try it out"** feature.
* **ReDoc**: Visit `http://127.0.0.1:8000/redoc` for a clean, documentation-focused layout.

## 🛡️ Cybersecurity & AppSec Insights

This lab is built with a strong focus on cybersecurity. Here are the core security principles explored during this phase:

### 1. The Trust Boundary (Never Trust the Client)
Everything on the client-side (web browsers, mobile apps, custom proxies) is untrusted. 
* **The Lesson**: Developers cannot secure an application by simply hiding a button or modifying the user interface (e.g., hiding a "Delete" button from standard users). Attackers can intercept the network traffic with a tool like **Burp Suite** or **OWASP ZAP** and construct the delete request manually. All permissions, authentication, and validation must be checked on the **Server side**.

### 2. Information Disclosure via Headers
* **The Lesson**: Servers frequently output identification headers like `Server: gunicorn/19.9.0` or `Server: Apache/2.4.41 (Ubuntu)`. In reconnaissance, this exposes the exact technologies and software versions running on the backend. Attackers cross-reference these versions with the Common Vulnerabilities and Exposures (CVE) databases to find public exploits. Hardening production servers involves hiding or spoofing these headers.

### 3. HTTP vs. HTTPS (Statelessness and Encryption)
* **HTTP** is like sending a postcard; data is in plaintext and vulnerable to sniffing and Man-in-the-Middle (MitM) attacks.
* **HTTPS** creates a TLS tunnel, acting like a sealed envelope.
* **API Best Practice**: Sensitive data (such as login credentials or tokens) must never be sent in the URL path or query parameters (e.g., `GET /api/login?user=admin&pass=secret`), because URLs are written to browser history, proxy server logs, and web server logs. They must always be sent encrypted inside the **Request Body** of a `POST` request over HTTPS.
